# Coding Task Report Format

Apply this when reporting on a coding task: progress updates, results, audits, CI or PR summaries.
Keep small answers small. A one-line fix gets the minimal form, not the full template.

## Principles

1. **Lead with status**: one line, with an emoji, before any detail.
2. **Tables for structured data**: checks, commits, branches, PRs, owners.
3. **Same emoji means the same thing**, every time (vocabulary below).
4. **Progressive disclosure**: summary, then details, then references.
5. **Code formatting for identifiers**: SHAs, paths, commands, env vars, run IDs, PR numbers in backticks.
6. **Report only what you verified.** If a step was skipped or a check failed, say so plainly.

## Visual vocabulary

| Emoji | Meaning | Use for |
|-------|---------|---------|
| ✅ | PASS / DONE / SAFE | passing checks, merged PRs, verified fixes |
| ❌ | FAIL / BLOCKED / UNSAFE | failing checks, blockers |
| ⏳ | PENDING / IN PROGRESS | running jobs, awaiting input |
| 🟡 | ACTIVE / WARNING | current branch, partial success, needs review |
| 🔴 | CRITICAL | security issues, data loss, urgent |
| 📋 | DOCS | reference docs, handoffs, specs |
| 🔧 | FIX / CONFIG | code changes, workflow edits, tooling |
| 📊 | METRICS | counts, measurements, benchmarks |

## Full template

```markdown
# [Topic] — [PR/Issue ref if any]

**Target**: `branch` (SHA `abc1234`)
**Status**: ✅ WORKING / ❌ BLOCKED / ⏳ PENDING
**Updated**: YYYY-MM-DD

## One-line summary
The **decision-critical fact** in bold.

## Status matrix
| Component | Status | Ref | Notes |
|-----------|--------|-----|-------|

## What worked
| Commit | Change | Verified |
|--------|--------|----------|

## What failed (blockers)
| Issue | Details | Owner |
|-------|---------|-------|

## Next steps
1. **Owner**: action
```

Drop any section that has nothing in it. Add "Team status" or "Before / After" tables only when they help.

## Table patterns

**Commit log**: `| Iteration | Commit | Fix | Files | Result |`
**Branch landscape**: `| Branch | Status | Notes |`, using ✅ MERGED, 🟡 ACTIVE, 🔴 STALE, PROTECTED.
**Quality gates**: `| Gate | Status | Required action |`

## Minimal update (default for small tasks)

```markdown
## Status: ✅ TESTS PASS / ❌ LINT FAIL

| Check | Result | Details |
|-------|--------|---------|

**Blocker**: one line. **Next**: one line.
```

## Rules

Do:
- Put context in headers, **bold** key values (**PASS**, **14 SCCs**), and use `---` between major sections.
- Use `>` blockquotes for important callouts.
- Link PRs and issues as full markdown links with `owner/repo`, never a bare `#123`.

Don't:
- Use ALL CAPS for emphasis, or mix status styles in one report.
- Write prose paragraphs for structured data.
- Claim a check passed unless you ran it.

## Boundaries

- This format is for chat reports. Commit messages, PR bodies and repo files follow the project's own conventions.
- Never add AI-attribution footers or "generated by" lines to anything this skill formats.
- Terminal rendering is GitHub-flavored markdown. Tables, task lists (`- [ ]`) and code fences work. Avoid HTML.
